## Root causes

**RC1. Marker pins are aggregates, so any edit that keeps the aggregate passes** (finding 3; fourth recurrence: W00 r1 RC4, r2 RC3, W00a RC1). checks.ts:222-227 compares only the count and the sum of the rows matching (field, account, month), and coverage (checks.ts:186-195) is keyed on that same triple. A +1/-1 cent pair, a swap of which row carries the marker, a priorYear row moved anywhere in 2024-12, or two May rows traded all keep count and sum. Can also bite: every kind W01 to W13, W20 and SK0 that registers faults (plan/cards/families/kind.md "Fault registration" says nothing about pins); SC2's R57 wording ("a one-cent change or an extra marked row") would bless the aggregate design.

**RC2. A check whose driving collection is empty passes vacuously, and the one rule written against it was wrong for C12** (findings 1, and the vacuous half of 2). W00a's fix list said "refuse a client with no accounts"; C12 has none by design, so the spec writer dropped the test (loader-input.acceptance.test.ts:11, amber) and nothing replaced it. With `accounts: []` no roll, coverage or file check runs; with `yearMonths` = [] (reversed year, checks.ts:114) the coverage loop at checks.ts:173 checks nothing. Can also bite: opening trial balance rows [] (legitimate only for a first year, C09); unadjusted or adjusted rows [] with no postings (tieOut, checks.ts:88, compares nothing); `owners: []` (schema.ts:39); a marker entry with no rows after the redesign; a client with no catalogue entries.

**RC3. Values are validated alone, never against their twin** (findings 2 and 5). yearStart and yearEnd are each a calendar date but never ordered; onboarding `financial_year_end` and `fiscal_year_start` are plain `z.string()` (load.ts:83-84) and never compared with fiscalYear. Can also bite: `incorporation_date` and `prior_year_closing_balances.as_of` (not read at all); unmarked transaction and adjusting-entry dates are only checked by month, so a row dated 2025-04-01 passes for a year starting 2025-04-15 (C09 shape); priorYear rows only need to be before yearStart (checks.ts:220), so 1990-01-01 passes; the statement month's written `rolls` is ignored and recomputed (load.ts:260); about 60 date-shaped paths exist in the sample JSON and the loader reads 8 of them.

**RC4. File checks look at the written name, not what it resolves to** (finding 4). `statSync` follows links (load.ts:247), and the realpath test (load.ts:242) only asks "still inside the folder", so accounts/zz.csv linked to ../answer-key.json passes and its lines count as export rows. Can also bite: `readClientJson` (load.ts:151) accepts answer-key.json or onboarding.json as a link to another client's file; `clientFolders` (load.ts:100) uses existsSync; `guardFiles` (load.ts:367, W00b's region) uses Dirent, which skips a link entirely, so the guard never scans the link itself (harmless only once the loader resolves every link). Keep the existing test load-files.test.ts:99 ("a link that stays inside the folder is fine", accounts/ to accounts/): the fix below allows it.

**RC5. Coercion and last-wins parsing turn missing or repeated data into plausible values** (finding 6). `recordsOf` turns a missing name into "undefined" (load.ts:287); `JSON.parse` keeps the last of two equal keys (load.ts:133), so a second "CHQ" in statementBalances silently replaces the first. Can also bite: `resolves()` on a repeated onboarding key (load.ts:292); `accountNo ?? ''` (load.ts:222) and a posting with neither `dr` nor `cr` becoming 0/0 (load.ts:226) (both to SC2, below); the spec fixtures sample-copy.ts:87-136 and sample-walk.ts parse with JSON.parse too (fine once the loader refuses repeats).
