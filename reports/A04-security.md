## Findings (all low)
**L1. Open follows a link swapped in after the lstat** (safe-read.ts:21). `openSync` has no `O_NOFOLLOW`. Scenario: the exchange writer flips `outbox/<id>.json` between a regular file and a symlink once a second while the job waits; one turn lands between lstat and open, and the open follows the link to a device (Linux: a tape or tty device whose open has side effects) or, on Windows with symlink rights, to `\\host\share\x`, which makes Windows offer the user's NTLM credentials to that host. The fstat check then says `gone` and nothing is read, but the open already happened. Fix (FX18): add `fs.constants.O_NOFOLLOW` where defined, as O_NONBLOCK is; a test plants the swap with a spied lstat.
**L2. A hard link passes as a regular file** (safe-read.ts:26-28). lstat and fstat both see a regular file with matching dev and ino. Scenario: the writer hard-links `outbox/<id>.json` to a file it cannot read but Returns can, on the same volume. Returns reads it in full (up to 4 MiB); the job fails "not JSON" or "not one result or refusal", so content does not leak, but the outcome is a small oracle on that file and Returns has read another owner's file. Fix (FX18): refuse `opened.nlink !== 1` as `not-a-file`; the project writes by temp file and rename, so a result always has one link.
**L3. The folder check is made once; the folders are trusted for hours afterwards** (engines.ts:198-205, 215, 217). Scenario: after `realFolder`, a writer with rights on the exchange root renames `inbox` and puts a link there: `renameSync` follows it and drops `<id>.json` (the redacted job) into, and over a same-named file in, any folder the user can write. Or it swaps `outbox` for a link to another folder: each poll then lists that folder and logs its file names and sizes into Returns' log, and reads `<id>.json` there. Impact is small (fixed name pattern, content never printed; a writer with root rights is already a process of the same user), hence low. Fix (FX18): re-check the folder's real path right before the rename and on each poll, and fail the job when it changed; SC12 R93 covers the kind.
**L4. A writer can grow memory and the log without bound** (engines.ts:149-159, runner.ts:71). `seen` lives as long as the runner and is never pruned; it is keyed by name, size and mtime. Scenario: the writer touches one stranger file every second, or creates 100,000 files: each new mtime or name adds a key and a log line, and every poll does a synchronous `readdirSync` of the whole folder on the event loop. Fix (FX18): cap the entries listed per poll and the lines logged per wait (one summary line past the cap), and clear `seen` entries for names gone from the folder; a rule in SC12 (R95's neighbour) that every set fed from an outside folder has a cap.
**L5. Text from outside goes verbatim and unbounded into the handler error and `jobs.last_error`** (engines.ts:145, runner.ts:110, runner.ts:167). A project refusal's `reason` and `problems` (any length up to the 4 MiB cap, newlines allowed) and F04 problems naming output keys the model chose become the thrown message. Scenario: a refusal file with a 4 MiB reason, or a reason holding newlines that read as forged log lines wherever `last_error` is printed. Fix (FX18): cap each string (say 500 characters, one line, control characters removed) before it joins the error, and say "(cut)" when cut.

Already in FX18 from the check, confirmed here: (a) fs errors thrown from `projectRun` carry the exchange path into `last_error` (engines.ts:197, 204, 205, 150), against the card's "no value is printed"; (b) `<waiting id>.<other ext>` is never logged (engines.ts:151); (c) the BlockStatement disable spans all of `realFolder` (engines.ts:163-174).

Note, not a finding: the recorded engine reads `__recordings__` with `readFileSync` and logs names unquoted (engines.ts:80-82); those are repo files, in R94's allowlist.
