## What was verified

- **No path to a non-local or live database.** target.ts:14-30 refuses DATABASE_URL (even empty), any variable whose name contains SUPABASE, a non-local PGHOST or PGHOSTADDR, and a non-numeric PGPORT; the url host is the literal 127.0.0.1 and the user the literal postgres. index.ts:26-40 hands the driver fields (host, port, user, database), so PGHOST, PGUSER and PGDATABASE cannot override them; `pg` never reads DATABASE_URL. Every client and pool (index.ts:110, 278, 289, 303, 310, 328, 335) is built from that one url, with only the database name changed (withDatabase, :84-88). global-setup.ts calls testDbTarget before any connection; createTemplate calls it again (:344). The no-direct-driver scan (pg16.acceptance.test.ts) covers pg, pg-pool and postgres; `pg` is imported only in src/core/db/index.ts. Switch off: PGlite only, no socket.
- **No password in a url, message or log.** The url never carries a password; PGPASSWORD (or the throwaway local default) goes to the driver as a field only. Refusal messages name the variable, never its value. Error wrapping (:247, :316) adds a role name or schema file name only. global-setup logs the boot time only.
- **Pooled connections after round 5.** `transaction` (:193-237): `begin` first, then inheritSession copies identity and settings inside the open transaction with `set local session authorization`, `set local role` and `set_config(name, value, true)` (:169-191); role and session_authorization are never copied by set_config. On release, always `rollback` then `discard all` (which runs SET SESSION AUTHORIZATION DEFAULT and RESET ALL as the superuser login); any failure there, or any custom-setting statement during the transaction, releases with a truthy value, so pg-pool destroys the connection (:228-235). The catch's rollback failure (:219-223) is not trusted: the finally repeats the rollback and destroys on failure, so no bare release follows a swallowed error. `set_config($n, ...)` takes the name from params (:142-147); a non-literal, non-$n name marks the handle opaque and the next transaction is refused naming the statement (:149, :170-172). T1 to T5 cover the poisoned cleanup, session authorization on the handle and inside a committed transaction, both set_config forms and role drop.
- **dropOwnedRoles** (:239-250): resets session authorization and role first; a failed drop fails close() naming the role, after the connections and the database are closed (:252-268). No swallow.

## Lows (no fix required for DB16)

1. index.ts:53-63, 292-295: `pg16RunId` prefers an inherited DB16_RUN_ID. An exported or stale value makes two runs share an id (the first teardown force-drops the other run's databases), and the value goes unescaped into quoted identifiers (:63, :306, :331) and a LIKE pattern (`%` and `\` are not escaped). Local throwaway cluster only, and setting env already means running code. Suggest: global setup always mints a fresh id, or the id must match `^[0-9a-z_]+$`.
2. index.ts:24: default local password `postgres`; role names in `drop owned by` / `drop role` quoted without escaping `"` (names come from pg_roles, test only). Already in DB16-check.md.
3. index.ts:219-223: an empty `catch {}` around the first rollback. Safe because the finally retries and destroys on failure; if R92 (SC11) scans `catch {}` as well as `.catch(() => undefined)`, give this one an allow-list entry with that reason.
4. The clean release relies on Postgres 16.5 or later, where SET SESSION AUTHORIZATION really resets a SET ROLE (CVE-2024-10978). The box runs 16.14. checker.md and cloud-worker-run.md say "Postgres 16" only; a "16.5 or later" line would hold this.

## New edge cases for SC11 (landing rule: not DB16 failures)

- **A tx used after its transaction ends is not refused** (index.ts:197-209 has no closed flag). A call issued after the finally (a promise chain inside fn that is never awaited) runs on a released pooled connection: a session-level `set role` there would outlive `discard all` and reach the next transaction. Rule test: every tx method throws once the transaction has ended, on both backends.
- **Custom-setting detection is text-based and misses some forms** (index.ts:137, 142, 149): `set_config (` with a space before the parenthesis, a quoted name (`set "app"."x" = ...`), or a name with `$` is neither carried nor marked opaque, so the transaction silently runs without it. No schema file and no product module uses custom settings today (grep: none outside src/core/db and spec tests), so this fails closed for now. Rule test: each form is carried or refused.
- **Role tracking by pg_roles diff** (index.ts:150-153): pg_roles is cluster-wide, so a role another worker creates inside the same window is counted as this handle's, and close() then drops it or fails (loud, flaky). A role created in a transaction that rolls back is still listed, so `drop owned by` fails close(). Roles made outside `create role|user` text (a DO block, `create group`) are never tracked. A handle left in an aborted block fails `reset session authorization` before the drop loop, and the first failed drop stops the loop, leaving later roles. All loud; R91 (pg_roles compared at setup and teardown) catches what remains.
- **Session characteristics** (`default_transaction_read_only`, `default_transaction_isolation`) are copied with set_config after `begin`, so they do not apply to the transaction already started. Parity only: it fails loud, never falsely green.
- Already known (findings-4 item 7): a temp table made in a transaction is not visible to the handle; statements after `tx.rollback()` autocommit; `discard all` drops named prepared statements.
