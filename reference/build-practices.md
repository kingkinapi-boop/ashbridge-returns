# Build practices (research for the Lead)

Scout research, 28 Sep 2026. Reference, not authority: the blueprint and `decisions/` win. Anything below that would change a clause, cost money or add scheduled GitHub automation is red for Zo.
Each item: verdict, what to do, [fact] (the source says it) or [inference] (my reading for this build), where it goes, source. docs.claude.com now redirects to platform.claude.com/docs, so Anthropic links use that host. All sources read 28 Sep 2026.

## Top 8 to adopt first

1. Builders cannot edit acceptance tests or golden files (PreToolUse hook in builder.md), and a SubagentStop gate runs them before any report (1.4, 3.9).
2. zod v4 contracts as the one source for types, module-edge validation and AI JSON Schemas; dependency-cruiser enforces module boundaries (3.4, 3.5).
3. fast-check property tests on money, tax and allocation code, with one written dollar-rounding rule for GIFI (2.7, 2.8).
4. Golden-file tests for every Taxprep CSV, owned by the spec-writer, plus a spreadsheet-mangled fault set (2.10 to 2.12).
5. StrykerJS mutation testing on changed money, tax and CSV files only, incremental, with a break threshold in the checker (2.13 to 2.15).
6. A fast, deterministic test base: PGlite template plus `clone()`, unit and db Vitest projects, agent reporter, pinned clock, TZ and locale, flaky counts as failed (2.1 to 2.6, 2.20, 2.21).
7. AI steps: structured outputs with code-checked box citations (native citations cannot be combined with them), OCR text as JSON-encoded untrusted data with planted injections, exact model IDs, recorded answers, an in-repo eval set (4.1, 4.2, 4.4 to 4.8).
8. R00 supply-chain and app baseline: exact pins, `min-release-age=7`, `npm ci`, audit signatures, gitleaks, a patched Next.js with a Data Access Layer (6.2, 6.3, 6.5, 6.6).

## 1 Spec-driven development

- **1.1 SKIP** installing GitHub Spec Kit. [fact] It supports Claude Code (key `claude`, installs skills in `.claude/skills`) and runs constitution, specify, plan, tasks, implement, converge; Thoughtworks Radar vol 34 (Apr 2026) rates it Assess and warns of "instruction bloat" and "overly verbose markdown outputs". [inference] Blueprint clauses, cards and the spec-writer already form a spec-anchored flow; a second spec layer would duplicate it and drift. Where: none. Sources: https://github.com/github/spec-kit , https://github.github.io/spec-kit/reference/integrations.html , https://www.thoughtworks.com/en-us/radar/languages-and-frameworks/github-spec-kit
- **1.2 ADOPT** thin specs: one clause is one testable sentence, one card is one reviewable change. [fact] Böckeler (15 Oct 2025) found SDD tools made "a LOT of markdown files" that were repetitive, and saw agents both skip and over-follow instructions; the Radar rates spec-driven development Assess ("handcrafting detailed rules for AI ultimately doesn't scale"). Where: Lead card writing; reviewer check on card length. Sources: https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html , https://www.thoughtworks.com/en-us/radar/techniques/spec-driven-development
- **1.3 ADOPT** (keep) tests first, by a different agent, committed before the builder starts. [fact] Claude Code best practices: "have one Claude write tests, then another write code to pass them"; Anthropic's harness post told agents "It is unacceptable to remove or edit tests". Where: spec-writer.md as is. Sources: https://code.claude.com/docs/en/best-practices , https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents
- **1.4 ADOPT** acceptance tests and goldens read-only for builders at the tool level, not only by the checker's diff. [fact] ImpossibleBench (ICLR 2026): read-only test access stopped test edits and kept legitimate performance, but did not stop special-casing; subagent frontmatter supports `hooks` that run only while that subagent is active. [inference] A PreToolUse hook in builder.md denies Edit and Write on the card's spec-commit test files and `**/__golden__/**`. Where: builder.md, `.claude/hooks`. Sources: https://arxiv.org/abs/2510.20270 , https://code.claude.com/docs/en/sub-agents
- **1.5 ADOPT LATER** holdout tests on hard cards. [fact] Hiding tests cut cheating to near zero but also lowered legitimate scores (ImpossibleBench). [inference] The spec-writer keeps 1 to 3 extra tests on a branch the builder never fetches; the checker runs them, so special-casing fails. Trigger: first hard card after R03, or the first special-casing a checker finds. Where: spec-writer.md, checker.md. Source: https://arxiv.org/abs/2510.20270
- **1.6 ADOPT** (keep) status in JSON, changed only after verification. [fact] Anthropic chose JSON for its feature list because "the model is less likely to inappropriately change or overwrite JSON files compared to Markdown files". [inference] Only the Lead sets a card `done` in `plan/slices.json`, after checker and tester PASS (lesson 18). Where: skill merge. Source: https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents
- **1.7 ADOPT** a plan consistency check (Spec Kit's "converge" idea without Spec Kit). [inference] Fail when a card cites a missing clause, a live clause has no card and is not in 11-not-building, two open cards share paths, or a card has no acceptance checks. Where: `tools/matrix.mjs --plan` or a new tool; reviewer check. Source: https://github.com/github/spec-kit
- **1.8 ADOPT** every card ends in an end-to-end check and every report shows evidence. [fact] Best practices: good specs "name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step"; "Have Claude show evidence rather than asserting success". Where: card template; builder report. Source: https://code.claude.com/docs/en/best-practices

## 2 Testing

### Mix, speed and determinism
- **2.1 ADOPT** most tests as pure unit tests (money, CSV, rules), PGlite integration tests per module, a few Playwright journeys per phase; the laptop runs only affected tests. [fact] `vitest --changed [since]` runs tests affected by changed files; `vitest related <files>` runs tests that cover named files. Where: R00 scripts, `tools/heavy.mjs` callers. Source: https://vitest.dev/guide/cli
- **2.2 ADOPT** two Vitest projects, `unit` (no database) and `db` (PGlite), so builders run the fast one first. [fact] `--project` selects projects by name or wildcard. Where: R00 `vitest.config.ts`. Source: https://vitest.dev/guide/cli
- **2.3 ADOPT** a PGlite template: load `db/schema/*.sql` once per worker, then `clone()` per test. [fact] `clone()` is for tests that "run on the same database without having to recreate the database each time"; `dumpDataDir()` and `loadDataDir` save and restore a data directory. Where: R00 `src/core/db`. Source: https://pglite.dev/docs/api
- **2.4 ADOPT** a Postgres version guard. [fact] PGlite is its own WASM Postgres build and is single user/connection. [inference] Its major version need not match the cloud's Postgres 16 or the live database: R00 logs `select version()` from both, the `db` project also runs on Postgres 16 in `check <card> full`, and the schema avoids features newer than the oldest. Where: R00, checker.md. Source: https://github.com/electric-sql/pglite
- **2.5 ADOPT** failure-only test output for agents. [fact] Vitest's minimal reporter (alias `agent`) prints only failed tests and their errors and is chosen automatically inside AI coding agents; the C compiler post says the harness "should not print thousands of useless bytes" and wants ERROR plus the reason on one line. Where: R00 scripts pass `--reporter=agent` explicitly; tools print one line per failure. Sources: https://vitest.dev/guide/reporters , https://www.anthropic.com/engineering/building-c-compiler
- **2.6 ADOPT** fixtures instead of shared setup: typed builders per contract with fixed defaults and overrides, a `db` fixture from the template, test-world kinds as fixtures. [fact] Vitest `test.extend<T>()` fixtures are created per test, only when used, and can depend on each other. [inference] No random personal data: names end "(Test)" (rule) and one generator owns SIN-like strings. Where: R04, R00. Source: https://vitest.dev/guide/test-context

### Money and tax arithmetic
- **2.7 ADOPT** fast-check property tests on every money and tax function. [fact] `@fast-check/vitest` adds `test.prop`; a failure prints a seed and path that replay it; `fc.configureGlobal` sets `numRuns`. [inference] Properties: adjusting entries net to zero; prorations and allocations sum exactly to the total; cents stay safe integers; ties are symmetric; a counterexample found once becomes a fixed example test (lesson 15). Where: rule code.md, spec-writer.md. Sources: https://fast-check.dev/docs/ecosystem/ , https://fast-check.dev/docs/tutorials/quick-start/read-test-reports/
- **2.8 ADOPT** one written rounding rule. [fact] GIFI amounts are reported in dollars without cents ($10,500.75 is reported as 10501). [inference] Rounding each line on its own can leave assets a dollar off liabilities plus equity (CK-10, CK-3); define the rule once in `src/core/money.ts` and property-test that rounded statements still tie or carry a recorded rounding item (log amber). Where: R01 or the money card. Source: https://www.canada.ca/en/revenue-agency/services/forms-publications/publications/rc4088/general-index-financial-information-gifi.html
- **2.9 ADOPT** (keep) a planted fault for every tie, reconciliation and flag, drawn from the test world's fault catalogue. [fact] "it's important that the task verifier is nearly perfect, otherwise Claude will solve the wrong problem". Where: R04, spec-writer.md step 4. Source: https://www.anthropic.com/engineering/building-c-compiler

### CSV round trip
- **2.10 ADOPT** golden files for every Taxprep file the system writes or reads (import file; exports 0 to 3 from the simulator), per test-world kind. [fact] Vitest `toMatchFileSnapshot()` compares against a named file of any extension; in CI Vitest writes no snapshots and missing or changed ones fail the run. Where: R03, R06 (simulator), R20 (mapping). Source: https://vitest.dev/guide/snapshot
- **2.11 ADOPT** goldens are acceptance files: only the spec-writer creates or updates them (`-u`), the checker diffs them against the spec commit, and the 1.4 hook blocks builder edits. [inference] Where: checker.md step 2, spec-writer.md. Source: https://vitest.dev/guide/snapshot
- **2.12 ADOPT** a fault set for RT-9 and RT-12: scientific notation, lost leading zeros, reformatted dates, other separators, a BOM, CRLF, Windows-1252 accents, blank versus "0". [fact] CCH: a blank cell is not imported and "0" imports zero; the Taxprep export page warns that Excel may misread custom separators (per `reference/sources.md`). [inference] Each must be refused with a reason; the simulator emits them (RT-23). Where: R03, R06. Sources: https://support.cchifirm.ca/en/content/cch_ifirm/tax/tax_-_csv_syntax.htm , https://www.taxprep.com/assistance/T2/2025/v20/en-ca/Content/ImportExport/Export.htm

### Mutation testing (proves the tests catch faults)
- **2.13 ADOPT** StrykerJS with the Vitest runner, on changed files only, for money, tax-rule, CSV and citation-check code. [fact] The Vitest runner always uses per-test coverage and by default runs only tests related to mutated files; `--mutate` takes comma-separated files and line ranges (`src/app.js:5-7`). [inference] Script `mutate:changed` passes the card's changed `src` files from `git diff --name-only origin/main...HEAD`. Where: package.json script; `check <card> full`. Sources: https://stryker-mutator.io/docs/stryker-js/vitest-runner/ , https://stryker-mutator.io/docs/stryker-js/configuration/
- **2.14 ADOPT** `--incremental`, with the incremental file cached per branch, and `--force` after config or dependency changes. [fact] Incremental mode reuses results when code and tests did not change, but "will not detect any changes you've made in files other than mutated files and test files" (dependencies, env, `.snap`). Where: same script. Source: https://stryker-mutator.io/docs/stryker-js/incremental/
- **2.15 ADOPT** a break threshold on changed money, tax and CSV files: start at 70, raise at the phase 3 gate. [fact] A score below `thresholds.break` makes Stryker exit 1 (defaults: high 80, low 60, break off). [inference] The checker lists surviving mutants as missing tests. Where: stryker config; checker.md. Source: https://stryker-mutator.io/docs/stryker-js/configuration/
- **2.16 SKIP** whole-repo and screen mutation runs. [fact] The Vitest runner does not support browser mode. [inference] Cost without signal; screens get ARIA and axe checks instead. Where: none. Source: https://stryker-mutator.io/docs/stryker-js/vitest-runner/

### Browser tests
- **2.17 ADOPT** ARIA snapshots as the main structural check on review screens. [fact] `toMatchAriaSnapshot` compares the accessibility tree as YAML, with partial matching and regex names. [inference] Text diffs, the same on every OS, and a natural test for the fixed section order and "approve stays off" (RV). Where: phase 5 screen cards; tester. Source: https://playwright.dev/docs/aria-snapshots
- **2.18 ADOPT** axe on every screen journey through one fixture. [fact] Playwright's guide uses `AxeBuilder` with tags `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, a shared fixture, and `exclude`, `disableRules` or violation fingerprints for known issues, and says many problems are only found by manual testing. Where: first screen card; tester keeps the keyboard walk. Source: https://playwright.dev/docs/accessibility-testing
- **2.19 ADOPT LATER** pixel screenshots for a few dense screens. [fact] "Browser rendering can vary based on the host OS"; "run tests in the same environment where the baseline screenshots were generated"; file names carry browser and platform; `maxDiffPixelRatio`, `threshold`, `animations` and `stylePath` reduce noise. [inference] Baselines only from the cloud Linux runner, never the Windows laptop. Trigger: phase 5 layouts settled. Sources: https://playwright.dev/docs/test-snapshots , https://playwright.dev/docs/api/class-testconfig
- **2.20 ADOPT** flaky counts as failed. [fact] Playwright `failOnFlakyTests` (v1.52) exits with an error when any test is flaky and `forbidOnly` blocks `test.only`; Vitest retries default to 0. [inference] Cloud runs use `retries: 1` only to detect flakiness; a flaky test gets a fix card the same day and is never skipped without one. Where: `playwright.config.ts` (R00), rule code.md. Sources: https://playwright.dev/docs/api/class-testconfig , https://vitest.dev/guide/cli
- **2.21 ADOPT** pinned clocks, time zone and locale everywhere. [fact] `page.clock.setFixedTime` fixes `Date.now()`; `clock.install` allows pause and fast-forward; `timezoneId` and `locale` set the browser, while the runner's zone comes from `TZ`. [inference] `TZ=America/Toronto` for Vitest and Playwright, `timezoneId: 'America/Toronto'`, `locale: 'en-CA'`, plus the injectable clock (rule). Where: R00 configs. Sources: https://playwright.dev/docs/clock , https://playwright.dev/docs/emulation
- **2.22 ADOPT** a timing test for RV-4 (a source opens in under one second). [inference] The app sets `performance.mark` on click and on source paint; the journey reads the measure and fails above 1000 ms on the cloud runner, on the largest test-world return. Where: source-viewer card; tester. Source: https://developer.mozilla.org/en-US/docs/Web/API/Performance_API/User_timing

## 3 Parallel agents without collisions

- **3.1 ADOPT** trunk-based limits. [fact] DORA: three or fewer active branches, branches that last hours, merges to trunk at least daily, no code freezes. [inference] In-flight cards never exceed the mode's slots; a card branch older than 24 hours is a Reviewer SLOW signal. Where: skills dispatch and merge; reviewer check. Source: https://dora.dev/capabilities/trunk-based-development/
- **3.2 ADOPT** test the merge result, not the branch. [fact] A merge queue checks changes "applied to the latest version of the target branch", but private repos get merge queues only in organizations on Enterprise Cloud, and protected branches on private repos need Pro or higher. [inference] The merge skill merges main into the branch and reruns checks whenever main moved after the green run; the local main-push-guard hook stays the required check. Where: skill merge step 1. Sources: https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue , https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches
- **3.3 ADOPT** CI on branches once Zo says yes (TODO item 2): typecheck, lint, unit tests on `claude/**`, `npm ci` with cache, one concurrency group per branch with `cancel-in-progress: true`. [fact] GitHub Free includes 2,000 minutes and 500 MB a month for private repos, and usage is blocked, not billed, without a payment method; `cancel-in-progress` cancels the older run in a group. Where: R00 `.github/workflows/checks.yml`. Sources: https://docs.github.com/en/billing/concepts/product-billing/github-actions , https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency
- **3.4 ADOPT** contracts first as zod v4 schemas in `src/contracts`: types by `z.infer`, validation at module edges, JSON Schema for AI steps. [fact] `z.toJSONSchema()` is built in (draft-2020-12 by default) and throws on types JSON Schema cannot hold (bigint, date, map, set, transform). [inference] So contracts carry cents as integers and dates as ISO strings. Where: R01, R03; rule code.md. Source: https://zod.dev/json-schema
- **3.5 ADOPT** module boundaries as a checked rule: a module imports only `src/contracts`, `src/core` and its own folder (ARC-7). [fact] dependency-cruiser validates "forbidden" dependency rules from a config file and runs in CI as a structural linter. Where: R00 (config and script); checker.md. Source: https://github.com/sverweij/dependency-cruiser
- **3.6 ADOPT** serialise shared files: `package.json` and the lockfile, contract index files, schema file order. [fact] In Anthropic's 16-agent build "Merge conflicts are frequent". [inference] A new dependency is its own small card; `tools/next.mjs` already refuses overlapping paths. Where: Lead card writing. Source: https://www.anthropic.com/engineering/building-c-compiler
- **3.7 ADOPT** `merge=union` for append-only logs only (`plan/metrics.jsonl`, `plan/ledger.jsonl`, `plan/AMBER.md`). [fact] Git's union driver takes "lines from both versions, instead of leaving conflict markers", in random order, and "the user should verify the result". [inference] Safe for one-record-per-line files; never for code or JSON documents. Where: `.gitattributes` (add to R00 paths). Source: https://git-scm.com/docs/gitattributes
- **3.8 ADOPT** generated files (matrix output, progress page) change only on main, at merge, by the Lead (lesson 30); a card branch that touches them fails scope. [inference] Where: `tools/scope.mjs` deny list; checker.md. Source: https://www.anthropic.com/engineering/building-c-compiler
- **3.9 ADOPT** a deterministic stop gate for builders. [fact] "a Stop hook runs your check as a script and blocks the turn from ending until it passes", with a cap on consecutive blocks; Stop hooks in subagent frontmatter become SubagentStop. [inference] A builder cannot report until typecheck and the card's acceptance tests pass (through `tools/heavy.mjs` on the laptop). Where: builder.md hooks. Sources: https://code.claude.com/docs/en/best-practices , https://code.claude.com/docs/en/sub-agents
- **3.10 SKIP** lock-file task claiming and agent teams. [fact] The C compiler agents claimed tasks by writing files to `current_tasks/`; Claude Code agent teams are experimental and off by default. [inference] Lead-assigned cards with path checks are stricter and cheaper. Where: none. Sources: https://www.anthropic.com/engineering/building-c-compiler , https://code.claude.com/docs/en/best-practices

## 4 LLM features in the product

- **4.1 ADOPT** structured outputs for every AI step (AI-1). [fact] `output_config.format` with a JSON Schema is GA and constrained decoding makes responses "Always valid"; objects need `additionalProperties: false`; `minimum`, `maximum`, `minLength`, `maxLength` are unsupported; the TS SDK has `zodOutputFormat` with `client.messages.parse()`; compiled grammars are cached 24 hours from last use. [inference] Ranges and cross-field rules are checked by zod after the call. Where: R03, first AI card. Source: https://platform.claude.com/docs/en/build-with-claude/structured-outputs
- **4.2 ADOPT** the blueprint's own citations (box ids with quoted text, checked by code, AI-4); SKIP Claude's native citations on JSON steps. [fact] "Citations cannot be used together with structured outputs" (the API returns 400), and image citations are not supported. Where: R03 AI contracts. Source: https://platform.claude.com/docs/en/build-with-claude/citations
- **4.3 ADOPT LATER** native citations as an A/B for the red team (AI-3) at LIVE-7. [fact] They are "guaranteed to contain valid pointers to the provided documents", `cited_text` is not billed as output, and custom content documents are not chunked further, so one OCR line per block gives block-index citations. [inference] Map block to box id; AI-4 still verifies. Trigger: the AI-11 test set exists. Source: https://platform.claude.com/docs/en/build-with-claude/citations
- **4.4 ADOPT** prompt-injection defences for document text (AI-8). [fact] Anthropic lists "OCR output from an uploaded file" as indirect injection and advises: untrusted content only in tool results, saying what it is and where it came from, a system-prompt rule that it is data, JSON-encoded untrusted strings, least privilege, optional small-model screening, and red-teaming with planted injections. [inference] OCR words go in as JSON with box ids; the test world plants injection text in documents with an expected no-effect result. Where: first AI card; R04 faults; reviewer check. Source: https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks
- **4.5 ADOPT** exact model IDs in every AI-10 stamp. [fact] "Every Claude model ID is a pinned snapshot, including the dateless IDs used from the 4.6 generation on"; retirements get at least 60 days' notice; Opus 5.5 and Sonnet 5.5 retire no sooner than 22 and 28 Sep 2027, Haiku 4.5 (`claude-haiku-4-5-20251001`) no sooner than 15 Oct 2026. [inference] Stamp model, effort and prompt hash; check the deprecations page at each phase gate. Where: R03 version stamp; reviewer check. Sources: https://platform.claude.com/docs/en/about-claude/models/overview , https://platform.claude.com/docs/en/about-claude/model-deprecations
- **4.6 ADOPT** no reliance on temperature. [fact] `temperature`, `top_p` and `top_k` return 400 at non-default values on Claude 4.7 and later. [inference] Unit tests use recorded answers; evals repeat runs and report pass^k. Where: rule code.md (AI code). Source: https://platform.claude.com/docs/en/about-claude/model-deprecations
- **4.7 ADOPT** recorded answers keyed by model id, prompt hash and input hash; a changed key fails with "re-record" instead of passing silently. [fact] `claude -p --json-schema` returns "validated JSON output matching a JSON Schema" in print mode, so re-recording can use the subscription stand-in (ARC-6). Where: AI adapter stand-in card. Source: https://code.claude.com/docs/en/cli-reference
- **4.8 ADOPT** an in-repo eval set for AI-11, no new tool: test-world returns with planted faults, code graders first, model graders only where code cannot judge, repeated runs. [fact] Anthropic: automate grading, code grading is fastest and most reliable, "Prioritize volume over quality"; its Jan 2026 evals post: grade outcomes, read transcripts, keep capability and regression evals apart, pass@k and pass^k answer different questions. Where: Vitest project `evals` outside the default run; AI-11 card. Sources: https://platform.claude.com/docs/en/test-and-evaluate/develop-tests , https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents
- **4.9 SKIP** promptfoo for now. [fact] OpenAI agreed to acquire Promptfoo (announced 9 Mar 2026); it stays MIT-licensed. [inference] A YAML eval layer would duplicate the code graders; revisit only to generate injection cases. Where: none. Source: https://www.promptfoo.dev/blog/promptfoo-joining-openai/
- **4.10 ADOPT** prompt caching on a stable prefix (tools, system prompt, check library, schema), volatile parts last. [fact] Cache reads cost 0.1x base input (0.05x on Opus 5.5), writes 1.25x (5 minutes) or 2x (1 hour); minimum prefix 512 tokens on Opus 5.5 and Sonnet 5.5; at most 4 breakpoints; changing tools, citations or the output format invalidates it; check `cache_read_input_tokens`. Where: AI adapter live side. Source: https://platform.claude.com/docs/en/build-with-claude/prompt-caching
- **4.11 ADOPT LATER** the Message Batches API for bulk AI work: AI-11 runs, re-checking all returns after a prompt change, the overnight red team. [fact] 50% of standard prices; most batches end within an hour and expire at 24 hours; results kept 29 days and returned in any order (match on `custom_id`); up to 100,000 requests or 256 MB; use the 1-hour cache for shared context. Trigger: live AI key (LIVE-7). Source: https://platform.claude.com/docs/en/build-with-claude/batch-processing
- **4.12 SKIP** Claude's PDF input as the document reader. [fact] Each PDF page goes in as an image plus extracted text (about 1,500 to 3,000 tokens a page), and PDF citations point to pages, not boxes. [inference] No word boxes, so AI-4 could not check them; send OCR words instead. Where: none. Source: https://platform.claude.com/docs/en/build-with-claude/pdf-support
- **4.13 ADOPT LATER** (red, LIVE-3) state where AI inference runs. [fact] Claude API `inference_geo` offers "us" (1.1x price on 4.6 and later) or "global", with no Canadian option; AWS describes Claude reaching ca-central-1 customers by cross-Region inference to US or global Regions; citations and PDF input are ZDR-eligible except "Covered Models". [inference] Masking before any AI call (AI-9) carries the privacy load; tell Zo the location at LIVE-3. Sources: https://platform.claude.com/docs/en/manage-claude/data-residency , https://aws.amazon.com/blogs/machine-learning/accelerate-generative-ai-innovation-in-canada-with-amazon-bedrock-cross-region-inference

## 5 OCR with word-level boxes

- **5.1 ADOPT** the pdf.js text layer for born-digital PDFs in the build. [fact] `getTextContent()` returns text items with a string, transform, width and height. [inference] Items are runs of text, not words: split them by glyph widths and test against test-world PDFs where the true box of every value is known. Where: phase 2 reading card. Source: https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html
- **5.2 ADOPT** tesseract.js for scans in the build. [fact] v7, Apache 2.0, runs in Node; since v6 all outputs other than text are off by default and must be requested per call (for example `{ hocr: true }`) to get word boxes. [inference] Pin the package and language data so results repeat; store results for tests (ARC-6). Where: phase 2 reading card. Source: https://github.com/naptha/tesseract.js
- **5.3 ADOPT** one normalised word format for every engine: text, page, box in PDF points, confidence, engine and version, plus the raw response. [fact] Azure Read returns words with polygon and confidence. [inference] Engines stay swappable and results replayable (ARC-6, AI-10). Where: the reading contract (R03 or the phase 2 contract card).
