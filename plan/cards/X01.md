## Goal
Each return gets exactly one tier, green, amber or red, from the approved rules in the blueprint's tier table, worked out in code, with the reasons that put it there. Every term in the table has one testable meaning kept as data. The tier sets queue order and how much the CPA's screen highlights, and never reduces the review below the full return (RULE-7, RV-8). Only people approve the rules; no AI output sets, lowers or clears a tier.

## Build
- `data/tiers/rules.json` (data before code): one record per item in the blueprint's tier table (green, amber and red conditions), each with a stable code never renumbered, its tier, a plain name, its testable meaning (the check ids, facts and review lines it reads, and any threshold) and a source link or the word `flag` where no source settles it. Thresholds the firm chose (within 25% of last year; fewer than 50 reviewed files; passive income over $50,000 where the rule is the firm's reading) are firm parameters here, named as the firm's own, changed only by an amber row. The file has a `version`, stored with every tier result (ARC-10).
- `src/modules/tiers/terms.ts`: one function per term, `(inputs) => met | not_met | not_checked`, reading only what its record names. Missing evidence gives `not_checked` ("not checked: no evidence"), never met. A term that needs a person's reading (personal services business signs, special items) reads the flags the check library raised: a flag raised in the latest run counts as met for amber or red whether or not a person answered it, so no answer, and no AI output, lowers a tier; code never settles a flag (CK-5).
- `src/modules/tiers/tier.ts`: `tierOf(returnId, deps)` returns the tier and its reasons (rule codes and the figures read). Red if any red term is met. Otherwise amber if any amber term is met, or any green condition is `not_met` or `not_checked`. Green only when every green condition is met, so an open exception or a failed hard tie can never give green. A return code cannot decide is amber with the reason "not checked".
- `src/modules/tiers/highlight.ts` (RV-8): `highlightsFor(tier, lines)` returns what the CPA screen emphasises (green: pinned flags; amber: also the five largest lines and every amber-dot line; red: also every changed, amber or red line), always beside the full ordered section list, so the screen cannot show less than the whole return.
- `src/modules/tiers/queue.ts`: `queueOrder(items)` (RV-20, Z20-4, A433): overdue first, then red, amber, green, then due date, then longest waiting (`waitingSince`, passed in by the caller), then id; stable and total. Overdue means the pinned clock is past the filing due date (FLOW-12); a past balance-due date does not count as overdue.
- `db/schema/72_tiers.sql`: a new table of tier results (tier, reasons, rules version, input stamps), append-only with `refuse_change` triggers on update, delete and truncate, row-level security on, a CHECK list on tier. New terms are logged as amber when first defined (CK-40).

## Acceptance checks
1. CK-40: every item in the blueprint's tier table has a record in `rules.json` with a code, tier, testable meaning and a source or `flag`; a sweep fails on a table item with no record or a record with a blank source.
2. CK-40: each of the thirteen test-world kinds lands on its expected tier from a golden file (K13, the catch-up kind, lands red); a kind planting one red term lands red whatever else is clean.
3. CK-40 property (fast-check, fixed seed): adding a met term never lowers the tier; term order never changes the tier; only all-green-met with no amber or red term gives green.
4. CK-40 with CK-2: with any green condition's evidence missing the tier is amber and the reason says not checked, never green.
5. CK-40 arithmetic (property, integer cents): "within 25% of last year" is exact at the boundary (25.00% passes, one cent over fails); last year zero or absent is not checked.
6. RULE-8 with CK-5: a term resting on an open flag stays met while the flag is open; an answered flag still counts as met; no planted AI result lowers or clears a tier (AI-7).
7. RV-8, RULE-7: each tier's highlight set is the stated one and the full section list is always present; none returns fewer sections than the return has.
8. RV-20: `queueOrder` puts overdue first, then red, amber, green, then due date, then longest waiting (`waitingSince`), then id; any shuffle gives the same order; a return past only its balance-due date is not overdue.
9. ARC-10: each tier row stores the rules version and input stamps; a second run adds a row and leaves the first byte-equal; UPDATE, DELETE and TRUNCATE are refused by the database.
