## Goal
A fact is "one value with a meaning", and the meaning is its fact key. One catalogue names every key once, with the type of value it holds and whether it is sensitive, so extraction (E01 and E10 to E25), the gap pass (G00), the question bank (G01, G10 to G17) and redaction (I00) all speak of the same facts. Data, not code: a new fact is a new entry.

## Build
- `src/contracts/facts.ts`: zod schema and types for one entry, and a pure `loadFactCatalogue(json)` that validates the whole file and returns a lookup (contracts may hold pure functions, as F09 does). An entry: `key` (dotted lower case, `<area>.<subject>.<measure>`, for example `bank.statement.closing_balance`, `t4.summary.total_employment_income`, `onboarding.shareholder.percent_common`), `valueType` (money in cents, date, text, count, percent in basis points, boolean, enum with its option ids), `period` (instant at a date, or a duration with start and end), `repeating` (none, or the row key that tells repeated rows apart, for example the slip number or the account), `sensitive` (none, `sin`, `birth_date`, `bank_account`; I00 masks these before any AI call and U02 on every screen), `suppliedBy` (the document kinds from E02's kinds list, `onboarding`, `qa`, `cra_capture`, `prior_return`, `qbo`, `judgment`), and a short staff label (no sentence: no final full stop, at most 60 characters).
- `data/facts/catalogue.json`: the keys the phase 1 work needs: every value the sixteen document kinds E10 to E25 read (statement opening and closing balances and lines, card and loan statement totals, trial balance lines, financial statement lines, invoice totals, last year's T2 summary values, notice of assessment values, CRA data capture values, HST return lines, T4 and T5 summary totals and slip values, OHIP payments, share register entries, resolution amounts and dates), every onboarding field the bridge (F07) reads into facts, and the facts the answer keys' flags rely on. Each key cites where its meaning comes from (a CRA form line, the onboarding contract field, or the answer key field).
- `DOCUMENT_KINDS` in `src/contracts/facts.ts`: the one list of document kind ids (the kinds E02 lists, one per extractor family E10 to E25 plus the CRA notices and slips E02 names). E02's `kinds.json` uses exactly these ids, so this card does not wait for E02.
- The file carries a version (a hash of its content) that every fact's version stamp names (ARC-10 is E01's).

## Acceptance checks
1. EV-5: `loadFactCatalogue` accepts the committed catalogue and refuses, each with the reason, a duplicate key, a key not in the dotted pattern, an unknown value type, a repeating key with no row key, and a label that ends in a full stop or runs past 60 characters.
2. EV-10: every `suppliedBy` entry is one of `DOCUMENT_KINDS` or one of the named non-document sources; an unknown one is refused.
3. SEC-4, AI-9: every key whose value is a SIN, a date of birth or a bank or card account number is marked sensitive with its kind (the test lists the known ones: shareholder SIN, director birth date, bank account number, card number); a key whose name says "sin", "birth" or "account_number" with `sensitive: none` fails.
4. EV-5: every fact key used in the ten sample clients' answer-key flags and every onboarding field the onboarding contract lists for the bridge is in the catalogue (the test reads both lists).
5. EV-5: the version changes when any entry changes and stays the same when the file is re-saved with the same content.
