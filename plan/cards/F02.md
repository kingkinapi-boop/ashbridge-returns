## Goal
A return's states and moves as code: one function moves a return and refuses anything blueprint 02's table does not allow.

## Build
- States and moves exactly as blueprint 02's table. Each move has a named guard; guards later cards own start as "not built yet" and refuse.
- `move(returnId, to, actor, why)` writes one state event (FLOW-1).
- "Waiting on the client" as a dated flag, not a state (FLOW-3).
- `voidApproval(returnId, changedItems)`: when any changed item is in the approval fingerprint, the approval is void and the state returns to trace; otherwise nothing changes (FLOW-5). The fingerprint's shape comes from FLOW-4; T06 computes it.
- Due dates (FLOW-7, FLOW-12): filing on the same day of the sixth month after year end, or the last day of that month when the year end is a month end (a 28 Feb year end is due 31 Aug); balance due two months after year end, or three when the return is marked as meeting CRA's CCPC conditions (a boolean for now). Cite CRA T4012 in the test.
- Holds (FLOW-10): one holder per return; a hold expires after 4 hours idle (a named constant; amber A11).

## Acceptance checks
1. FLOW-2: every move not in the table is refused; every move in it is allowed when its guard passes.
2. FLOW-1: every move writes exactly one event with who, when, from, to and why.
3. FLOW-4, FLOW-5: a change to an item in the approval fingerprint (the shape FLOW-4 names) voids approval and returns the state to trace; an unrelated change does not.
4. FLOW-7, FLOW-12: due dates for year ends 31 Dec, 30 Jun, 28 Feb (non-leap), 29 Feb (leap) and a short first year, with the three-month case.
5. FLOW-10: a second preparer cannot take a held return; an expired hold can be taken.
6. FLOW-3: setting "waiting on the client" writes a dated flag with one event and leaves the state as it was (no state named waiting exists); clearing it writes an event and keeps the earlier dates.
