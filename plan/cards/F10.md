## Goal
The product needs one place that joins the modules into the return pipeline (intake, read, facts, books, figures, import file, Taxprep round trip, trace, checks), because F00's rule lets a module import only `src/contracts`, `src/core` and its own folder. That place is `src/pipeline/`, the one composition root. The walking skeleton (SK0) then runs through the real pipeline, with its stubs injected only from test code, and every later step card fills one step file instead of inventing its own wiring.

## The rule (written into `.dependency-cruiser.cjs` and `src/pipeline/README.md`)
- `src/pipeline/` may import `src/contracts`, `src/core` and each module's public `src/modules/<m>/index.ts`, never a module's inner files.
- No module imports `src/pipeline/`. Modules never import each other; when a module needs another's service (jobs, storage, reading, AI), it takes the contract interface as a parameter and the pipeline passes the implementation in.
- `src/app/` (screens and server actions) may import `src/pipeline/`, `src/ui/`, `src/contracts`, `src/core` and module `index.ts` files; for work that crosses modules it calls the pipeline.
- `src/pipeline/testing.ts` (step overrides) may be imported only from `e2e/**` and `*.test.ts` files. Nothing under `src/` imports `e2e/` or `testworld/`.

## Build
- `src/pipeline/order.ts`: the fixed step order: `intake`, `read`, `facts`, `books`, `gaps`, `figures`, `import`, `taxprep`, `trace`, `checks`. `e2e/_harness/pipeline.ts` takes its step list and order from here (one source of truth; JH0's glob of `e2e/steps/<step>.ts` stays).
- `src/pipeline/steps/<step>.ts`: one file per step, each exporting the step's handler (input and result schemas from `src/contracts`, `run`). This card writes all ten: `read` wired to the real reading adapter (A01, through `src/modules/ocr/index.ts`; E02 later replaces it with split and classify once E00 reads at intake), `taxprep` wired to the Taxprep adapter (the simulator S00 as the free stand-in; the live side is people importing and exporting by hand, off here), and the other eight as "not built" placeholders that return `{ status: 'not built', step }`. A later step card replaces exactly its own file, so step cards never share a register.
- `e2e/steps/<step>.ts` for all ten steps: each is a thin call into the pipeline's step, so JH0's journeys run the product's real steps and a placeholder step shows as "not built" there too. Step cards never edit these files.
- `src/pipeline/run.ts`: `runPipeline(returnId, deps)`: enqueues each step as a job through the jobs contract (F06), kind `pipeline:<step>`, idempotency key = return id + step + hash of the step's input, in order; a step's input is the earlier steps' results. A failed or dead step stops the later ones and the run's result names the step and the reason; a "not built" step is reported as such and never as a pass. Each step result carries its version stamp (ARC-10: the step name, the code release and whatever versions the module returned).
- `src/pipeline/handlers.ts`: the job handler map: every `pipeline:<step>` kind plus the handlers modules export for their own jobs (for example A04's `ai:<step>`). This is the only place handlers are registered.
- `src/pipeline/deps.ts`: builds the real dependencies once (database, clock, jobs queue and runner from F06, file store and Drive stand-in from A05, the reading adapter) and passes them in.
- `src/pipeline/testing.ts`: `runPipelineWith(overrides)`: the same run with some step handlers replaced, for the skeleton and tests only.
- The skeleton moves onto the pipeline: `e2e/skeleton/` calls `runPipelineWith` with its stubs as overrides; every stub function moves to `e2e/skeleton/stubs.ts` and stays listed in `e2e/skeleton/stubs.md` with the card that replaces it. Anything SK0 built thinly that is not yet a listed stub (for example its trace) becomes one now. `e2e/steps/skeleton-*.ts` call the pipeline instead of wiring modules themselves.
