## Goal
One way for any AI step to run: the step hands the runner a job (step type, prompt version, model id, redacted inputs); the runner returns F04-checked output with its version stamp, or a refusal with the reason. In tests it replays recorded answers. For real runs it hands the job to a separate Claude Code project on the firm's subscription through a job exchange folder and reads back the project's JSON (ARC-22). There is no paid API engine and no key anywhere.

## Build
- `src/modules/ai/runner/`: `runAiStep(job) -> { output, stamp } | refusal`, with an engine switch: `recorded` (the default, and the only engine tests use) and `project` (the Claude Code project exchange, off by default). There is no API engine: asking for any other engine name is refused with "AI runs only through the Claude project (decision 0008)", and the package has no Anthropic SDK or other model-vendor dependency.
- Inputs: the job carries a redaction stamp (who redacted, redactor version). A job without one is refused with "inputs not redacted (AI-9)" before any engine runs. The redactor itself is I00's; this card only refuses unstamped input.
- Every output is validated with F04's validator for its step type (AI-1). A failing output is a refusal listing the problems and is counted against the step (a per-step counter of refusals the screens and the lesson list read later). It is never repaired by code.
- The stamp (AI-10): exact model id, prompt version and hash, input hash, OCR engine and version and mapping release as the caller gives them. Output with an incomplete stamp is refused.
- `recorded` engine: answers keyed by model id, prompt hash and input hash, stored as JSON under the calling card's `__recordings__/` folder. A missing key fails with "re-record" and the three key parts; it never passes silently and never calls the project.
- `project` engine (ARC-22): an exchange folder named by the setting `AI_EXCHANGE_DIR` (read by name through `src/core/env.ts`; no value is printed). Returns writes each queued job to `inbox/<job id>.json` (step type, prompt version, model id, the JSON Schema from `z.toJSONSchema()`, the redacted inputs) and, through the jobs contract (F06), keeps the job `running` until `outbox/<job id>.json` appears. It then reads, validates and stores the result. Files in `outbox/` that match no running job, or that hold anything but one JSON result, are ignored and logged by name only. The project has no other way to write to Returns. Without the setting the engine refuses to switch on.
- While go-live is off, the `project` engine runs only jobs whose return is made up (`is_test`), and refuses any other with the reason (SEC-11).
- The AI-11 gate: `data/ai/approved.json` lists the approved (step type, prompt version, model id) triples. The runner refuses a triple not on the list with "not approved: run the evaluation set first (AI-11)". The evaluation harness that adds triples is I40; this card ships the list with no triples and the check. Tests point the runner at their own list.
- `src/modules/ai/index.ts`: the module's public exports (I00 adds its own later).
- The job handler for `ai:<step>` jobs is exported for F10 to register; this module does not import the jobs module (F00's boundary rule), it uses `src/contracts/jobs.ts`.

## Acceptance checks
1. AI-1: the recorded answer for the fixture job comes back as F04-valid output with the stamp; the broken recorded answer is refused with F04's problem list and the step's refusal counter goes up by one.
2. AI-10: an output whose stamp lacks the model id, the prompt hash or the input hash is refused with the missing part named.
3. AI-9: a job with no redaction stamp is refused with "inputs not redacted" and no engine is called (spies on both engines show zero calls).
4. ARC-16: a job whose prompt hash or input hash differs from every recording fails with "re-record" and the three key parts; the project engine is not called.
5. ARC-22: with the fake project, a `project` job writes exactly one inbox file equal to the golden file; when the fake writes the outbox file, the job ends `done` with F04-valid output; an outbox file for an unknown job id, and a second file for the same job, are ignored and logged by file name only.
6. ARC-22, AI-1: an outbox result that fails F04's schema leaves the job failed with the problems; it is not stored as output.
7. ARC-6, ARC-20, END-8: the `project` engine is off by default; switching it on without `AI_EXCHANGE_DIR` is refused; with the setting it runs against the fake project; switching back to `recorded` works (both directions tested). Asking for an engine named `api` or `anthropic` is refused with the decision 0008 reason.
8. END-8: `package.json` has no Anthropic SDK or other model-vendor client, and no setting the runner reads holds a key (names checked only, never values).
9. SEC-11: while go-live is off, a `project` job for a return with `is_test = false` is refused with the reason and no inbox file is written.
10. AI-11: a job whose (step type, prompt version, model id) is not in `data/ai/approved.json` is refused with "not approved"; adding the triple to a temp copy of the list (the test points the runner at it) lets the same job run.
