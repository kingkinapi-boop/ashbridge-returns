## Fix round 1 (findings review, 1 Oct)
Inputs: `reports/F00-check.md` (FAIL at step 3), `reports/F00-build.md`, branch `claude/F00`. Rebuild on `claude/F00`; steps 1-2 of the check passed and stay as they are.

### Root causes
1. **The cold start lands in a test body, under a guessed timeout.** `cloneTestDb()` boots PGlite (WASM compile plus initdb) and loads the schema lazily inside the first test; the `db` project sets no `testTimeout`, `hookTimeout` or `globalSetup`, so the 5 s default decides (2 timeouts in 4 runs). Made worse by `npm test` running `unit` and `db` at the same time (`--project unit --project db` runs them together; the card says unit, then db), so the boot competes for CPU. The template sits in module state, and Vitest isolates each file, so every `*.db.test.ts` file pays the cold start again: "once per worker" is in fact once per file.
2. **The database test proves less than its name.** With no `db/schema/` folder (F01 makes it) nothing is loaded from a schema folder; the clone check passes on any error (`rejects.toThrow()` with no reason); clones are never closed.
3. **No gate catches flakiness before the checker.** The builder ran `npm test` once and saw green. Nothing repeats cold runs, and nothing stops a later test file from making its own `new PGlite()`.

### Where else it bites
- Every card with `*.db.test.ts` files: F01, F06, F07, A06, E00, E02, L00 and all later modules. Each new file adds a cold start (minutes once there are dozens) and each new schema file in `db/schema/` makes the boot slower, so a pass today fails at F01.
- GitHub CI (`npm test` on a 2-core runner) and the train on a cold cloud machine: slowest boot, so most timeouts; the laptop (Windows, Defender scanning the WASM, `maxWorkers` 2, Zo working on it) is slower still.
- JH0's journeys (`e2e/_harness/fixtures.ts`: a fresh database per test) and `dev:testworld`: if they build their own PGlite they repeat the fault inside Playwright, where a slow first test reads as flaky and `failOnFlakyTests` fails the run.
- ARC-4 and testing.md: the `db` project must also run on Postgres 16 in cloud checks (JH0 acceptance 7). The helper must keep one small interface that a Postgres 16 backend can sit behind later; do not build that backend here.

### Fix list for the builder, in order
1. `package.json`: `test` runs `vitest run --project unit` and then, only if it passes, `vitest run --project db`; `test:changed` the same.
2. `src/core/db/index.ts`: `createTemplate(schemaDir)` boots PGlite once, applies `*.sql` in name order, and fails with the file name on a bad file; `schemaDir` defaults to `db/schema` resolved from the repo root, not `process.cwd()`. `cloneTestDb()` only clones the ready template and registers the clone so it is closed after each test. It never boots PGlite itself; if the template is not ready it throws "db warm-up did not run".
3. `vitest.config.ts`, `db` project: a `globalSetup` that boots PGlite and loads the schema once (fail fast on a bad schema, print the boot time in ms); a `setupFiles` entry whose `beforeAll` builds this worker's template, with its own measured `hookTimeout`; `isolate: false` (or the Vitest 5 equivalent) so the template lives once per worker, not once per file; an `afterEach` that closes clones and resets the clock with `setClock(systemClock)` so nothing leaks between files.
4. Timeouts by measurement, not guessed: time 10 cold `db` runs on the cloud machine and 3 through `node tools/heavy.mjs --` on the laptop; write the p95 of the boot and of a test body in the build report. `hookTimeout` = 3 times the slowest boot, at least 30 s; `testTimeout` for `db` = 3 times the slowest test body, at least 5 s and at most 15 s (a test body never pays a boot). Put the numbers in a comment next to the settings.
5. `npm run test:flake` (a script in `tools/`, plain Node): runs the `db` project in 5 fresh processes, cold each time, with the shuffle seed pinned; any failure or timeout fails it, and it prints the slowest boot. The checker runs it on every card that touches `src/core/db/**`, `db/schema/**` or `vitest.config.ts` (the Lead adds this to `.claude/agents/checker.md`).
6. Rewrite `db.db.test.ts` as a builder unit test on a planted schema folder (below); keep the ARC-4 name.
7. Then finish the check that stopped: e2e (acceptance 4), mutation on `money.ts` and `ids.ts`, the security review (SEC-10), scope. Acceptance 7 (CRLF on the laptop) is a Lead check after the build. Dependabot alerts stay with the Lead (permission denied in the cloud).

### Risks of the fix, and what to re-test
- `isolate: false` shares module state across files in a worker: the global clock (`setClock`) and any module cache can leak. The `afterEach` reset covers the clock; re-run the `db` project shuffled (`test:flake`). If leaks appear, keep isolation and load the template from a data dump made in `globalSetup` (`dumpDataDir`, then `loadDataDir` per file) instead.
- A larger `hookTimeout` could hide a real hang: the boot time is printed on every run and `test:flake` reports the slowest, so growth is visible.
- Running unit then db makes `npm test` a little longer on CI; the minutes are small next to the timeouts it removes. Re-test: `npm test`, `npm run test:flake`, the GitHub workflow on the branch, `npm run e2e` in the cloud, the CRLF check on the laptop.
