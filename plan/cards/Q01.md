## Goal
Every reconciliation explains its difference only with typed, sourced items a person accepted, of a type the check may use, and rounding explains at most one dollar. The type table is data with codes that never change meaning, so a new type is a data row and an amber row, not code.

## Build
- `data/checks/reconciling-items.json`: one entry per type, R01 to R29, exactly as the blueprint table: `code`, `name` (the snake_case name), a staff label, the checks that may use it (from the x marks: `CK-13`, `CK-20` to `CK-26`, `CK-44`, `CK-45`), the source (the research file or clause) and `addedBy` (the amber row, for any type after R29). The firm parameter `roundingLimitCents: 100` sits in the same file, marked as the firm's own (CK-50).
- `src/modules/checks/reconciling/types.ts`: `loadItemTypes(json)` validates the file: codes `R` plus two digits, unique and contiguous from R01; names unique; every allowed check is one of the ten reconciliation checks in the table. A committed snapshot of the code-to-name pairs (`__golden__/codes.json`) is compared on every run, so a renumbered or renamed code fails (CK-49). Every F05 code is in the file with the same number; a code beyond F05's list is refused until the contract lists it (a new type is an amber row plus a contract line).
- `src/modules/checks/reconciling/items.ts`: an item record: type code, amount in cents, source (a document id and page; R22 also needs a written note), status `proposed` or `accepted`, proposer (a person or an AI step) and `acceptedBy` (a person, never an AI or system actor) with the time. `proposeItem(checkId, reconciliationId, item, proposer)` stores a proposal (AI may propose, CK-4); `acceptItem(itemId, person)` stores the acceptance as a new row in Q00's `reconciling_items` table. Code refuses an item whose type the check does not allow, an item with no source, an item with amount zero, and an acceptance by anyone who is not a person (CK-48).
- `src/modules/checks/reconciling/apply.ts`: `itemsFor(checkId, reconciliationId)` returns only accepted items, in F05's `ReconcilingItem` shape with `acceptedBy` set, for Q00 to pass to `reconcile`; proposed items are listed for the person but never reduce the remainder. Rounding (CK-50): at most one R21 item per reconciliation, with an absolute amount at most the limit; a larger or second one is refused, so the amount stays unexplained.

## Acceptance checks
1. CK-49: the data file loads; its codes match F05's `RECONCILING_ITEM_CODES` one for one; the code-to-name pairs equal the golden snapshot; a copy with a renumbered code, a gap, a duplicate, a renamed type, or a new code F05 does not list fails with the reason.
2. CK-48: for every cell of the blueprint table (29 types by 10 checks, generated from the data file and compared with a hand-typed copy of the table's x marks), an allowed type is accepted and any other is refused with "type not allowed for CK-NN".
3. CK-48: an item with no source, an R22 item with no note (blank as a class: empty, spaces, NBSP, zero-width), an item with amount zero, and an acceptance by an AI step or the system are each refused; an accepted item stores who accepted it and when.
4. CK-4: a proposed item does not change the unexplained remainder; once a person accepts it, the remainder falls by exactly its amount.
5. CK-50 property (fixed seed): every non-zero R21 amount with absolute value at most the limit is accepted and every larger one refused, both signs (a zero amount is refused, per acceptance 3); at the edge, 100 cents is accepted and 101 (or minus 101) refused; a second R21 item on the same reconciliation is refused; a test with a changed limit in a copy of the data file shows the limit is read from data.
6. CK-4 property (fast-check, fixed seed): for any accepted items, the unexplained remainder equals the difference less the items' sum in integer cents, and no ordering of the items changes it.
7. CK-50 with CK-3: the caller sets the statement's document id and page on the R21 item F05's `roundStatementToDollars` returns (its own source is the text "rounding of statement lines to whole dollars"); it then passes `acceptItem` whenever its absolute amount is at most the limit.
