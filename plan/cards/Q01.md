## Goal
Every reconciliation explains its difference only with typed, sourced items a person accepted, of a type the check is allowed to use, and rounding explains at most one dollar. The type table is data with codes that never change meaning, so a new type is a data row and an amber row, not code.

## Build
- `data/checks/reconciling-items.json`: one entry per type R01 to R29 exactly as the blueprint table: `code`, `name` (the snake_case name in the table), a staff label (no sentence), the checks that may use it (`CK-13`, `CK-20` to `CK-26`, `CK-44`, `CK-45`), the source (research file or clause), and `addedBy` (the amber row for any type after R29). The firm parameter `roundingLimitCents: 100` sits in the same file, marked as the firm's own (CK-50).
- `src/modules/checks/reconciling/types.ts`: `loadItemTypes(json)` validates the file: codes `R` plus two digits, unique, contiguous from R01; names unique; every allowed check is a reconciliation in the CK-4 table. A committed snapshot of the code-to-name pairs (`__golden__/codes.json`) is compared on every run, so a renumbered or renamed code fails (CK-49).
- `src/modules/checks/reconciling/items.ts`: an item record: type code, amount in cents, source (document id and page, or ledger record id), status `proposed` or `accepted`, proposer (a person or an AI step), and `acceptedBy` (a person, never an AI or system actor) with the time. `proposeItem` stores a proposal (AI may propose, CK-4); `acceptItem(itemId, person)` accepts it. Code refuses an item whose type the check does not allow, an item with no source, and acceptance by a non-person (CK-48).
- `src/modules/checks/reconciling/apply.ts`: `itemsFor(checkId, reconciliationId)` returns only accepted items for F05's `reconcile`; proposed items are listed but never reduce the remainder. Rounding (CK-50): at most one R21 item per reconciliation, and its absolute amount at most the limit; a larger one is refused, so the amount stays unexplained.
- `// @mutate` on `items.ts` and `apply.ts`; mutation 100 per marked file (ARC-15).

## Acceptance checks
1. CK-49: the data file loads; its codes equal F05's `RECONCILING_ITEM_CODES` exactly; the code-to-name pairs equal the golden snapshot; a file with a renumbered code, a gap, a duplicate or a renamed type fails with the reason.
2. CK-48: for every check column in the blueprint table, each allowed type is accepted and each other type is refused with "type not allowed for CK-NN" (one generated test per cell of the table: 29 types by 10 checks).
3. CK-48: an item with no source, or accepted by an AI step or the system, is refused; an accepted item stores who accepted it and when.
4. CK-4: a proposed (not accepted) item does not change the unexplained remainder; once a person accepts it, the remainder falls by its amount exactly.
5. CK-50: an R21 item of 100 cents is accepted and of 101 cents refused; a second R21 item on the same reconciliation is refused; the limit is read from the data file (a test with a changed limit).
6. CK-4, ARC-13 property (fast-check, fixed seed): for any accepted items, unexplained equals the difference minus the items' sum in integer cents, and no ordering of items changes it.

## Not in this card
Any reconciliation check itself (Q cards for CK-13, CK-20 to CK-26, CK-44, CK-45). The screen where a person accepts items. AI proposing items (each check's own card).

## Ambers for the Lead
- One R21 item per reconciliation, absolute amount at most the limit; anything larger is refused, not split.
- `acceptedBy` stays optional in F05's contract; this card enforces it on accepted item records. A later contract card may tighten it.
- The firm rounding limit lives in the type table file rather than a separate parameters file.
