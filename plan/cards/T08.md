## Goal
When the CPA approves, Returns stores exactly what was approved: every value in the lock export, review lines included, and the id and version of every fact, entry and judgment input linked to them (FLOW-4). A later change to any of those voids the approval through F02, and the CPA later sees only the changed cells, before and after (FLOW-5). The record also keeps how the review went (RV-11), and nothing in it can be changed or deleted (SEC-7).

## Build
- `src/modules/approval/fingerprint.ts`: `buildFingerprint(returnId, lockExportId, deps)` returns F02's `ApprovalFingerprint` (cells, facts, entries, judgmentInputs). One cell per lock-export cell (input cells and T07's review lines), keyed by figure key and natural row key, never by copy number (LL-3), with its value as exported. One item per fact, adjusting entry and judgment input reached from those cells through T04's trace and L00's `sourcesOf`, with id and version. Canonical form: items sorted by key, JSON with sorted keys, values as strings; the hash is sha256 of that text. The item list is stored, not only the hash, so a change can be named.
- `src/modules/approval/source.ts`: implements F02's `ApprovalFingerprintSource.current(returnId)`: the standing approval and its items, or null after a void. It recomputes the hash from the stored items and refuses with "fingerprint does not match its items" on a mismatch. F10 passes it to `createLifecycle` as `approvals`.
- `src/modules/approval/sections.ts`: RV-1's review sections as ids in their fixed order (V03 imports them).
- `src/modules/approval/approve.ts`: `approve(returnId, actor, review, deps)` refuses: an actor whose role is not CPA (SEC-1, read through V00's access contract passed in); any AI or system actor (AI-7); a return not in `review` (FLOW-2); a review with any section unmarked (RV-10, naming them); a source-opened id that V00's source log does not hold for this actor and return. In one transaction it stores the approval row (hash, lock export id, version id), its items, the review record (per section: mark, who, when, seconds on it) and the sources opened (RV-11), F02's move to `approved`, L00's `acceptFacts`, and N00's `saveVersion(returnId, 'cpa-final', lockExportId, actor)`. Any failure keeps nothing.
- `src/modules/approval/void.ts`: `checkAgainstApproval(returnId, change, deps)` (FLOW-5): builds the items a change touches (a newly accepted export's cells, or a new version of a fact, entry or judgment input), compares them with the stored items and, when any fingerprinted value or version differs, calls F02's `voidApproval` with those `ChangedItem`s and stores each changed cell's before and after for the CPA's changed-cells view (RV-7). An unrelated or identical change does nothing. Callers: T02 (accepted export), L00 version events, B06, T09.
- `db/schema/60_versions.sql`: adds approval items, review sections, sources opened, voids and changed cells. Every new table is append-only with F01's `refuse_change` triggers on update, delete and truncate, with row-level security on. A void is a new row, never an edit of the approval.

## Acceptance checks
1. FLOW-4: for C01's test-world lock export with review lines, the fingerprint holds every input cell, every review line and every linked fact, entry and judgment input with its version, equal to a golden item list and hash; reordering export rows or renumbering copy numbers leaves the hash unchanged.
2. FLOW-4 property (fast-check, fixed seed): changing any one item's value or version changes the hash, and `checkAgainstApproval` names exactly that item.
3. FLOW-5: a later accepted export with one changed cell voids the approval, the return is in `trace`, and the changed-cells table holds that cell's before and after only; an export equal in every fingerprinted value leaves the approval standing and the state unchanged.
4. FLOW-5: a new version of a fact linked to an approved cell voids the approval and `current` then returns null; a new version of an unlinked fact changes nothing.
5. RV-11: an approval with every section marked stores each mark, who, when and the seconds on it, and every source opened with its log id; a source id the log does not hold for that CPA is refused and nothing is stored.
6. RV-11 with RV-10: a review with any section unmarked is refused naming those sections; nothing is stored and the state is unchanged.
7. SEC-1, AI-7 (permission check): approval by a preparer, ops, the owner without the CPA role, an AI actor or the system is refused with the reason; nothing is stored.
8. SEC-7: UPDATE, DELETE and TRUNCATE on `approvals` and on every table this card adds are refused by the database (db test on PGlite and Postgres 16).
9. SEC-7 tamper: an extra item row inserted straight into the database for a standing approval makes `current` refuse with "fingerprint does not match its items", and nothing is approved or voided on top of it.
10. LL-1: an approval saves exactly one `cpa-final` version through N00 in the same transaction; when that save throws (a fake), no approval, item, review row or state move is kept.
