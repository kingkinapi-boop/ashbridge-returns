## Goal
When the CPA approves, Returns stores exactly what was approved: every value in the lock export, review lines included, and the id and version of every fact, entry and judgment input behind them. Any later change to one of those items voids the approval and sends the return back to trace, and the CPA later sees only what changed. The approval record also keeps how the review went: each section's mark, the time on each section and every source opened.

## Build
- `src/modules/approval/fingerprint.ts`: `buildFingerprint(returnId, lockExportId, deps)` (FLOW-4): one item per lock export cell (input cells and T07's review lines, keyed by figure key and natural row key, never by copy number) with its value, plus one item per fact, adjusting entry and judgment input linked to those cells through T04's trace (id and version). Items are sorted and serialized canonically (JSON with sorted keys, values as strings, money as integer cents) and hashed with sha256; the item list is stored, not only the hash, so a change can be named.
- `src/modules/approval/sections.ts`: the review sections in RV-1's fixed order, as ids (the CPA review screen, V03, imports them from here).
- `src/modules/approval/approve.ts`: `approve(returnId, actor, review, deps)`: refuses an actor without the CPA role, any AI or system actor (AI-7), a return not in the state F02 allows to move to approved, and a review record missing a mark on any section (RV-10). Stores in one transaction: the approval (fingerprint hash and items, lock export id), the review record (per section: mark, who, when, seconds spent; every source opened with its source log id) (RV-11), F02's state move, and N00's `saveVersion(returnId, 'cpa-final', lockExportId, actor)`.
- `src/modules/approval/void.ts`: `checkAgainstApproval(returnId, currentItems, deps)` (FLOW-5): compares current items with the stored fingerprint and, when any fingerprinted item differs, calls F02's `voidApproval` with the changed items and stores each changed cell's before and after for the CPA's changed-cells view; an unrelated change does nothing. Callers: a newly accepted export (T02), a fact, entry or judgment input version change (L00 events), B06 and T09.
- `db/schema/60_versions.sql`: the approval items, review sections, sources opened and changed-cell tables, all append-only (UPDATE, DELETE and TRUNCATE refused by trigger, as F01's tables) (SEC-7). A voided approval is a new void row, never an edit.

## Acceptance checks
1. FLOW-4: for the C01 test-world lock export, the fingerprint holds every input cell and every review line, and every linked fact, entry and judgment input with its version; the same inputs give the same hash (fixed golden hash), and reordering export rows or copy numbers does not change it.
2. FLOW-4 property (fast-check, fixed seed): changing any one item's value or version changes the hash and names exactly that item.
3. FLOW-5: a later accepted export with one changed cell voids the approval, moves the return to trace through F02, and stores that cell's before and after only; an export identical in every fingerprinted value leaves the approval standing.
4. FLOW-5: a new version of a fact linked to an approved cell voids the approval; a new version of an unlinked fact does not.
5. RV-11, RV-10: an approval with every section marked stores each mark, its time and every source opened; one with any section unmarked is refused, naming the sections.
6. SEC-1, AI-7: approval by a preparer, ops, an AI actor or the system is refused with the reason.
7. SEC-7: UPDATE, DELETE and TRUNCATE on the approval, approval item, review section, source opened and changed-cell tables are refused by the database (a db test).
8. LL-1: an approval saves exactly one `cpa-final` version through N00 in the same transaction; if that save fails, nothing is stored.
