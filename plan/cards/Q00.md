## Goal
One engine runs every check on a return the same way: it finds the checks that apply, loads their inputs, says "not checked: no evidence" where evidence is missing, turns fails and unexplained remainders into exceptions with a dollar amount and tax effect, sends every flag to a person, and hands the review one list sorted red first, then by dollar effect. The check cards (Q10 to Q47) and the AI checks (I01, I30) then only write a record and a rule.

## Build
- `src/modules/checks/engine/types.ts`: an engine check is F05's `CheckRecord` plus `severity` (`red` or `amber`) and `run(inputs)`, which returns an F05 `CheckResult`, plus for a reconciliation its F05 `Reconciliation`, plus for a flag its amount in cents (or no amount) and the evidence ids it rests on. Plain types, so a check in another module (the AI checks) matches them without importing across the module boundary.
- `src/modules/checks/engine/registry.ts` (CK-1): finds the `checks` module's own checks by folder (`src/modules/checks/{ties,reconciliations,flags}/<check id>/check.ts`, each exporting `check`) and takes checks from other modules passed in by the pipeline step. Each is validated with F05's `validateCheckRecord`; a failing record, a duplicate id, a missing severity, or a kind whose result does not fit it (F05's `validateResultForCheck`) stops the run naming the module. Check cards never edit engine files.
- `src/modules/checks/engine/run.ts`: `runChecks(returnId, deps)`: for each check whose `appliesTo` holds, loads its named inputs through L00's contract, T07's review lines and stored AI results. Any input missing gives F05's `notChecked()` and `run` is not called (CK-2). A tie uses F05's `tie` (CK-3). A reconciliation uses F05's `reconcile` with the accepted items Q01 hands it, and only a non-zero unexplained remainder raises an exception, of exactly that amount (CK-4). A fail or remainder becomes an exception with its amount and tax effect, checked by F05's `validateException` (CK-6). A flag is stored open for a person with its amount; no engine code turns a flag into pass or fail (CK-5).
- `src/modules/checks/engine/taxEffect.ts`: `estimateTaxEffect(amountCents, rateBp)`. The rate is the return's own (Part I tax plus Ontario tax over taxable income, from T07's review lines) when taxable income is above zero; otherwise the firm parameter `defaultTaxRateBp` in `src/modules/checks/engine/parameters.json`, named as the firm's own and changed only by an amber row (start value 1220: the 9% federal and 3.2% Ontario small business rates, with source links). Integer cents, one rounding half away from zero.
- `src/modules/checks/engine/order.ts`: `orderForReview(items)` (EX-4): red before amber, then absolute tax effect, then absolute amount, then check id, then item id; items with no amount come after those with one in the same severity. Stable: the same items in any order give the same list.
- `db/schema/70_checks.sql`: adds `check_runs` (return, time from the injected clock, the input version stamps and code release, ARC-10); adds run id, severity and the outcome `not_checked` to F01's `check_results`; adds `flags` (result, amount, evidence ids) and `reconciling_items` (Q01 writes it: proposals and acceptances as new rows). Runs, results, flags and reconciling items are append-only (`refuse_change` triggers on update, delete and truncate); a new run never edits an old one.
- `src/pipeline/steps/checks.ts` replaces F10's placeholder: builds the registry with the list of checks from other modules (empty here; the AI cards add theirs) and runs `runChecks` after trace. The "one tie" stub leaves `e2e/skeleton/stubs.ts` and `stubs.md`; the skeleton's tie runs through the engine from `e2e/steps/skeleton-checks.ts`.
- `// @mutate` on `run.ts`, `taxEffect.ts`, `order.ts` and `registry.ts`; mutation 100 per marked file (ARC-15).

## Acceptance checks
1. CK-1: three fixture checks (a tie, a reconciliation, a flag) in the folder layout are found and run; a fixture with a blank source link, a duplicate id, no severity, or a tie that returns a flag stops the run naming the module.
2. CK-2: with one named input missing, the stored outcome is `not_checked` with "not checked: no evidence", a spy shows `run` was not called, and `summarizeResults` never counts it as a pass.
3. CK-3: the fixture tie fails at 100 cents apart and passes at 99 cents.
4. CK-4: a reconciliation whose accepted items explain the whole difference raises nothing; with one dollar unexplained it raises one exception of exactly 100 cents, storing both amounts, the difference and the items.
5. CK-4 property (fast-check, fixed seed): for any two amounts and items, the exception amount equals the difference less the items' sum in integer cents, and an exception exists only when that is not zero.
6. CK-5: a flag is stored open for a person whatever its rule returns beside it (a planted check returns a flag with an extra `pass: true` field); a sweep of the engine's exports finds no function that returns pass or fail from a flag.
7. CK-6 property (fast-check, fixed seed): every exception carries an amount and a tax effect in integer cents, and the tax effect equals the amount times the rate in basis points over 10,000, rounded once half away from zero; with taxable income zero or below, the firm default rate is used and the result names it as the firm's.
8. EX-4: a mixed list of flags and exceptions orders red first, then by absolute tax effect, then amount, then id; any shuffle of the input gives the same order (property, fixed seed).
9. CK-2 with ARC-10: every run stores its input version stamps; a second run adds rows and leaves the first byte-equal; UPDATE, DELETE and TRUNCATE on runs, results, flags and reconciling items are refused by the database (db test).
10. CK-3 with ARC-7: the "one tie" stub is gone from `stubs.ts` and `stubs.md`, the C01 skeleton journey still passes, and its tie result comes from `runChecks`.
