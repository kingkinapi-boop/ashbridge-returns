## Goal
Every exception Q00 raises gets exactly one answer from a person: fixed, explained (with a source or a reason), or accepted risk for the CPA to judge. Code refuses an answer with no source or reason, or one that only says "per client" or the like. If last year's return had the same exception with an accepted explanation, that explanation is offered as a proposal and never applied by itself. Nothing but a person's answer changes an exception's status.

## Build
- `src/modules/exceptions/answer.ts` (EX-1, EX-2): `answerException(exceptionId, answer, actor, deps)`. Three kinds. The target is an exception or a flag (Q00's `flags`), exactly one of the two; a flag takes the same three kinds. `fixed`: names what changed (a version id or a cell key). `explained`: a source pointer of one of EV-5's kinds, or a written reason that passes the weak-answer rule. `accepted_risk`: a written reason; the exception then waits for the CPA to judge (RV-24) and is not closed. Refuses an unknown exception, a second answer to an answered one (a changed answer is a new row that supersedes, never an edit), and any actor that is not a person with the preparer, CPA or owner role (SEC-1, read through V00's access contract passed in). An AI or system actor is refused (AI-7).
- `src/modules/exceptions/weak.ts` and `data/exceptions/weak-answers.json` (EX-2, data before code): a list of phrases that say nothing ("per client", "client said", "as discussed", "n/a", "ok", "see above" and the like, each with a stable code, never renumbered) and a minimum word count (firm parameter, start value 4, named as the firm's own, changed only by an amber row). A reason is weak when, after lowercasing and removing punctuation, it is blank (text.ts), is only a listed phrase, or has fewer words than the minimum. A weak phrase beside a real source pointer passes on the pointer. The refusal names the rule it failed.
- `src/modules/exceptions/prior.ts` (EX-3): `proposeFromLastYear(exceptionId, deps)` finds, in last year's accepted return of the same client, an exception with the same check id and the same natural key (not the same amount) whose explanation was accepted, and returns a proposal holding that answer, its year and its source. A proposal is its own record and never creates an answer. A person accepts it through `answerException` with the proposal id, which copies the text and source in as that person's answer and refuses if the source no longer resolves.
- `src/modules/exceptions/status.ts`: `statusOf(exception, answers)` returns `open`, `answered` or `awaiting_cpa`; it works the same for a flag. An answer never changes the exception's amount, tax effect or EX-4 sort position (EV-12: an exception stays a red flag until a person answers).
- `db/schema/71_exceptions.sql`: a new migration (no edit of landed 70): tables `exception_answers` (kind, source pointer, `supersedes`, `proposal_id`, and `flag_id` with a CHECK that exactly one of exception id and flag id is set) and `answer_proposals`, append-only with F01's `refuse_change` triggers on update, delete and truncate, row-level security on, CHECK lists on kind and status.
- `// @mutate` on `answer.ts`, `weak.ts`, `prior.ts` and `status.ts`; mutation 100 per marked file (ARC-15).

## Acceptance checks
1. EX-1: each of the three kinds is stored once with author, time and the exception it answers; a fourth kind, a missing kind or an unknown exception id is refused. Each kind is stored for a flag; an answer naming both or neither target is refused.
2. EX-2: a table of weak answers ("per client", "Per Client.", " PER CLIENT ", "n/a", blank, three words) is refused naming the rule; a real source pointer or a four-word reason passes; a weak phrase beside a real pointer passes on the pointer.
3. EX-2 property (fast-check, fixed seed): case, spacing and trailing punctuation never change whether a reason is weak.
4. EX-3: with a test-world prior year holding the same exception and an accepted explanation, a proposal is returned and no answer row exists until a person accepts it; a different check id or key, or an unaccepted prior answer, gives no proposal.
5. EX-3: accepting a proposal whose source no longer resolves is refused and nothing is stored.
6. AI-7, SEC-1 (permission check): an AI actor, the system, ops and a client are refused with the reason; nothing is stored and the status is unchanged.
7. EX-1 with EV-12: after an accepted-risk answer `statusOf` is `awaiting_cpa`, not closed; the exception's amount, tax effect and sort position are unchanged (property, fixed seed).
8. SEC-7: UPDATE, DELETE and TRUNCATE on the new tables are refused by the database (db test, PGlite and Postgres 16); a changed answer is a new row.
9. AI-7 sweep: no export of the module moves an exception's status without a person's answer call (a code sweep, as for CK-5).
