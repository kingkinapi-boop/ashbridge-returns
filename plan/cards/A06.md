## Goal
Every staff screen needs to know who is signed in and in which roles. This card gives Returns per-person sign-in with a second factor, the four roles, and server-side sessions, behind an adapter whose free stand-in is a fixed set of made-up test users and whose live slot is off with no key. Screens and who-sees-which-return (SEC-2) are V00's; this card answers "who is this, and what roles do they hold".

## Build
- `src/contracts/auth.ts`: `Role` is exactly `preparer`, `ops`, `cpa`, `owner`. `StaffUser` (id, display name, roles: one or more). `Session` (session id, user id, roles, signed in at, last seen at, expires at). The adapter interface: `startSignIn(userId, password) -> challenge | refusal`, `finishSignIn(challenge, code) -> session | refusal`, `getSession(token) -> session | none`, `touch(token)`, `signOut(token)`, `isLive`. Other modules and screens take this interface as a parameter (F10's rule).
- `db/schema/15_auth.sql` (schema `returns`, row-level security on, no policies, `is_test`): staff users and their roles, sessions (only the sha256 of the session token is stored, never the token), and sign-in events (who, when, success or the refusal reason; never the password or the code). Sign-in events are append-only (trigger refuses update and delete).
- `src/modules/auth/testusers/`: the stand-in engine `testusers`, the default. Eight made-up users, two per role, named "... (Test)", plus one user who holds both `cpa` and `owner` (as Zo will). Passwords are checked against scrypt hashes (`node:crypto`); the second factor is a 6-digit time-based one-time code (RFC 6238, 30-second steps, SHA-1, one step of drift allowed), written here with `node:crypto`, no new dependency. Each test user's password and code seed are derived at run time from the user id and a fixed public string, so no secret-looking value is committed and journeys can sign in; `src/modules/auth/testing.ts` exposes `testCredentials(userId)` and may be imported only from `e2e/**` and tests.
- Rules: a code is accepted once (reuse in the same step is refused); five failed attempts lock the user for 15 minutes; a session expires after 30 minutes idle and after 12 hours in all; tokens are 32 random bytes; every refusal names its reason for the event log but the caller only ever sees "sign-in failed" (no telling which part was wrong). All times come from the injected clock.
- Live slot (ARC-6, ARC-20): engine `live` exists by name, is off, holds no key and refuses with "live sign-in is off until go-live"; the engine is chosen by the setting `AUTH_ENGINE` read by name through `src/core/env.ts`. GL1 builds the live side.
- SEC-11: while go-live is off, the stand-in refuses any user whose display name lacks "(Test)".
- `src/modules/auth/index.ts`: the module's public exports (not `testing.ts`).

## Acceptance checks
1. SEC-1: a test user signs in only with the right password and then the right one-time code for the pinned clock; the session lists exactly the user's roles; the dual-role user's session lists `cpa` and `owner`.
2. SEC-1: a wrong password, a wrong code, a code from three steps ago and a code used twice are each refused with "sign-in failed" to the caller and the true reason in the sign-in event.
3. SEC-1: five failed attempts lock the user; a sixth attempt with the right password and code is refused until 15 minutes pass on the pinned clock, then it works.
4. SEC-1: a session is valid at 29 minutes idle, gone at 31; `touch` extends it; nothing survives 12 hours; `signOut` ends it at once.
5. SEC-1: `Role` accepts exactly the four roles; a user row with any other role is refused by the database.
6. SEC-10: the sessions table holds no column equal to any issued token (the test checks every row); no log line or sign-in event holds a password, code or token (a planted-value scan of the captured log); no file under `src/modules/auth/` matches the gitleaks rules.
7. ARC-6, ARC-20, END-8: the engine is `testusers` by default; `AUTH_ENGINE=live` refuses with "live sign-in is off until go-live"; switching back works (both directions tested); no setting the module reads holds a key.
8. SEC-11: a user without "(Test)" in the name cannot sign in while go-live is off.
9. SEC-7, SEC-6: sign-in events refuse update and delete; row-level security is on for the three tables, and a no-grants role reads zero rows from each.
