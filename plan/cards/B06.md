## Goal
Just before the check export (RT-19), Returns reads the client's books from QBO again and compares them with the books the approval used. Any changed balance, transaction or journal entry that feeds a figure is flagged "books changed after approval" with what changed, before and after, and voids the approval as FLOW-5 says, so the return goes back to trace. A change that feeds no figure is recorded and does not void. Nothing is written to QBO, ever.

## Spec
- Fixtures: B04 stand-in folders made at test time with `testworld/qbo/export.ts` for C01 and C02, each taken to an approved return (T08's fixtures); then copies of the stand-in folder changed in the test, one change per copy: one account's year-end balance changed by one cent (with its offset so the trial balance still balances); a transaction's amount changed; a transaction's date moved within the year; a transaction removed; a transaction added in an account that feeds a figure, with the account balance unchanged (offset inside the same account); a journal entry's memo reason changed; an adjusting entry's line amount changed; a new account mapped to a GIFI code whose cell is in the approved export; a new account with no GIFI mapping and a non-zero balance; a change only in an account that feeds no figure; a byte-identical re-read; a stand-in company named without "(Test)".
- Classes:
  - TB-11 (one class per kind of change): every change above that feeds a figure is flagged "books changed after approval" naming the kind (balance, transaction, journal entry), the QBO account and, for a transaction or entry, its id, with before and after in cents or text; the compare is by account id, transaction id (or B04's composite key) and journal entry id, never by row position.
  - TB-11 with FLOW-5: each such change voids the standing approval through the pipeline (no direct call to F02 or T08 from the test), naming exactly the fingerprinted items it feeds; the return is then in `trace`; the test runs F06's queue to idle before asserting the void. Property (fast-check, fixed seed): for any single change to one QBO row reached from the approval, the void names a non-empty set of items that includes the cells fed by that row; for any change to a row reached from no fingerprinted item, nothing is voided.
  - TB-11, no false alarm: the byte-identical re-read and a re-read whose only change feeds no figure leave the approval standing and the state unchanged; the second is recorded as "changed, feeds no figure" with before and after.
  - TB-11, a flag for a person: the new account with no GIFI mapping and a non-zero balance is flagged "books changed after approval: account not mapped" and the recheck result is `blocked` (T09 refuses the check export while it stands); it is never passed silently.
  - TB-11, the approved books: the books the approval used are exactly the QBO snapshots named by the pointers reached from the standing approval's items; an approval whose items name two different trial-balance snapshots of the same date is compared against each, and the result names both.
  - TB-10: the re-read is a new dated snapshot set through B04 (new snapshot rows, read-at from the pinned clock); the recheck record names the approved snapshots, the new ones, the approval id, who asked and when, and every difference; the record refuses UPDATE, DELETE and TRUNCATE (db test on PGlite and Postgres 16).
  - States: a recheck is refused naming the state for a return not in `approved`, `client_sign` or `ready_to_file` (no approval stands outside them).
  - Who: an ops person, the CPA or the owner may ask for a recheck; a preparer, an AI actor or the system acting alone is refused with the reason, and nothing is read.
  - OUT-3 and SEC-11: the recheck calls only B04's read methods (a spy transport sees reads only); the company named without "(Test)" is refused before any read.
- Golden file (`src/modules/books/recheck/__golden__/`): the recheck record for C01 with the one-cent balance change (differences, items voided, snapshots named).

## Build
- `src/contracts/books.ts` (B05's file; this card adds its shapes): the recheck result (`clean`, `voided`, `blocked`), each difference (kind, account, id, before, after, the fingerprinted items it feeds or "feeds no figure"), and `recheckBooks` on the books service interface.
- `src/modules/books/recheck/`:
  - `recheckBooks(returnId, actor, deps)`: checks the state and the actor, finds the standing approval through T08's `ApprovalFingerprintSource.current` (passed in through `src/contracts/lifecycle.ts`), collects the approved snapshots from the QBO pointers reached from its items (L00's `sourcesOf` for each fingerprinted cell's figure, and the pointers of its facts and entries), calls B04's `readBooks` for the same company and period, and compares the normalised rows: trial-balance lines by account id, transactions by id or composite key, journal entries by id with their lines and memo. Each difference is matched to the fingerprinted items it feeds: the cells whose `sourcesOf` reach the changed row, the facts and entries sourced from it, and, for an account new since the approved read, the cell of the GIFI code B01 maps it to in the fresh read.
  - Any difference that feeds an item: the result is `voided`, which means void requested; the approval-watch job (the step below, run through F06's queue) voids the approval. A difference that cannot be matched to an item but changes a balance (an unmapped new account): `blocked`, with the flag. Otherwise `clean`.
  - All money in integer cents through the money helpers; `// @mutate` on the compare and the matching files (mutation 100 per marked file, ARC-15).
- `db/schema/77_recheck.sql`: recheck runs and their differences, append-only with F01's `refuse_change` triggers, row-level security on, no policies, `is_test`, a foreign key on every return_id.
- `src/pipeline/steps/approval-watch.ts` and `src/pipeline/handlers.ts` (T08's step): a third trigger, "books rechecked", passes the voided items to T08's `checkAgainstApproval`, which voids through F02 and stores what changed. If T08's built `checkAgainstApproval` cannot take a list of fingerprinted items from a books recheck, the spec job reports it to the Lead before writing tests; this card never edits `src/modules/approval/`.
- `src/modules/books/index.ts`: exports `recheckBooks`.

## Check
By a third worker: acceptance tests unchanged since the spec commit, mutation 100 per `@mutate` file, the db tests on PGlite and Postgres 16, scope clean.

## Not in this card
