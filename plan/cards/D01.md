# D01 Staff screen map and navigation

Phase 1. Size M. Deps: none. Where: any.
Paths: design/map/**
Clauses: RV-1, RV-20, RV-30, RV-40, RV-50
Read: blueprint 02 (the lifecycle), 06 (screens), 08 (SEC-1, SEC-2), `reference/design-basis.md` section (c).

## Goal
Every staff screen named once, with its address, who may see it, what it is for and how people move between them, so the nine design cards and twelve screen cards agree before anything is drawn.

## Build
- `design/map/screens.md`: one row per screen: name, address, roles that see it (preparer, ops, CPA, owner, per SEC-2), the lifecycle states it serves (blueprint 02), the clauses it meets, its states worth designing (empty, normal, error, flagged, approved, void), and the GOV.UK or MOJ pattern it is built from (design basis section c).
- `design/map/navigation.md`: the service navigation by role, the identity bar on every return screen, where each button leads, what Back does, and the keyboard shortcuts (one list for the whole app).
- A simple diagram of the flow between screens (Mermaid in markdown).

## Acceptance checks
1. Every RV clause in blueprint 06 is met by at least one screen in the map.
2. Every lifecycle state with a person acting (blueprint 02) has a screen where that person acts.
3. No screen is reachable by a role that SEC-2 says may not see it.
4. Every button and link in the map leads to a named screen (no dead ends).
5. Every keyboard shortcut repeats a visible control and none clashes with browser or screen reader keys.

## Not in this card
Drawing the screens (D02 to D10).
