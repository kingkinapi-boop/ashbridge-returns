## Goal
Returns reads each client's books from QuickBooks Online and never writes to it. Every read (trial balance, transactions by account, journal entries, attachments) is kept as a dated, fingerprinted snapshot, so a QBO source pointer can always name the snapshot, the account and the transaction it came from, and the books can be compared again before filing (B06). Until go-live the books come from a free stand-in that serves the sample clients' QBO data; the API engines exist in code, switched off, with no key.

## What is not confirmed yet (the contract must say so)
The sandbox company's screens (1 Oct 2026, TB-13) settled what each report carries: the Trial Balance has account, debit and credit only, no ids; the Transaction List by Date, with Transaction ID and Memo added, has one row per transaction with its id and full memo; the General Ledger has type and number per line but no id, and its CSV drops the memo; the Journal report has the id only as a group heading and no memo; the journal entry form has no adjusting tick box (Adj reads No), so the memo marks an adjusting entry (TB-2, decision 0014). Still unconfirmed, because the API was not reached: the JSON shape of each report and entity, whether API report rows carry ids, and how long an attachment's download link lasts. So:
- `src/contracts/qbo.ts` defines Returns' own normalised shapes (below), not Intuit's JSON. It states in a header comment that the mapping from Intuit's report JSON is unconfirmed, with the date and the research file.
- The stand-in serves the normalised shapes directly, following the sample-client files.
- The API engines parse Intuit's JSON through one mapping file, `src/modules/qbo/api/mapping.ts`, tested only against fake responses in `src/modules/qbo/api/__fixtures__/unconfirmed/`, each marked `"confirmed": false`. When the sandbox check lands, the Lead adds a card to replace these fixtures with recorded sandbox responses and set them confirmed.
- Where a transaction id is missing from a row, the reader first joins it to the Transaction List by transaction type and number to get the Transaction ID (TB-13); failing that the pointer uses a composite key (date, type, number, account, amount in cents) and is marked `idKind: "composite"`; the books step flags it for a person (a flag rather than a silent pass). A row with a column the mapping does not know is refused with the column name, never dropped.

## Build
- `src/contracts/qbo.ts`: normalised shapes and the read-only adapter interface, which other modules take as a parameter (F10's rule):
  - `company(realm)`: realm id, legal name, fiscal year start month, country, home currency, whether it is a test company.
  - `trialBalance(realm, asOf, basis)`: rows of account id, number, name, type and sub-type, debit and credit in integer cents; `basis` is `accrual` (a request for any other basis is refused, TB-1).
  - `transactions(realm, accountId, from, to)`: rows of transaction id (or composite key), entity type, date, number, memo, account, amount in cents, the other accounts on the transaction, and attachment ids.
  - `journalEntries(realm, from, to)`: id, date, number, memo, Adjustment flag (or "not given"), lines (account, debit or credit in cents, line description), attachment ids.
  - `attachment(realm, attachmentId)`: name, type, bytes.
  - No write, update or delete method exists on the interface (OUT-3).
- `src/modules/qbo/snapshots/`: `readBooks(returnId, realm, yearStart, yearEnd, deps)` reads, in order, the company, the trial balance at year end, the trial balance at the day before year start (for TB-5's opening check), transactions for every account in the year, journal entries in the year, and every attachment those reference (copied at read time). Each read becomes one snapshot: the raw payload bytes stored write-once in the file store (A05, content-addressed), and a snapshot row with realm, kind, as-of or period, basis, engine and version, read-at from the injected clock, sha256 of the bytes, and the file key. Re-reading writes a new dated snapshot row even when the bytes are identical (they share the stored file). Attachments are fingerprinted like documents.
- QBO source pointers (EV-5, TB-10): `{ kind: "qbo", snapshotId, accountId, txnId?, lineNo?, idKind }`; `pointerFor(snapshot, row)` builds them and the schema refuses one with no snapshot or no account.
- Engines (ARC-6), chosen by the setting `QBO_ENGINE` read by name through `src/core/env.ts`:
  - `samples` (the default, the free stand-in): reads a local folder named by `QBO_STANDIN_DIR`, one subfolder per realm, holding `company.json`, `accounts.json`, `trial-balance-<date>.json`, `transactions/<account id>.json`, `journal-entries.json` and `attachments/`, in the normalised shapes. Nothing under `src/` imports `testworld/`.
  - `sandbox`: the API client pointed only at Intuit's sandbox host, off, no key in the repo; refuses with "QBO sandbox engine is off" unless switched on with its settings present (names checked only, values never printed).
  - `live`: the same client for the production host, refuses with "live QBO is off until go-live".
  - The API client (`src/modules/qbo/api/`) keeps to Intuit's published limits (no more than 10 requests a second and 500 a minute per company; on a 429 it waits 60 seconds on the injected clock and retries, at most 3 times) and is tested only against a local fake of the API (ARC-20).
- SEC-11: while go-live is off, every engine refuses a company whose legal name lacks "(Test)", before any read, and the `live` engine refuses always.
- `testworld/qbo/export.ts`: writes a stand-in folder for a test-world client from W00's model: the company; the chart of accounts from the answer key; each `qbo/*.csv` line as a booked transaction on its bank or card account, coded to the answer key's accounts (ids from the answer key's id rule); the answer key's adjusting entries as journal entries, with type, reason and sources written in the memo by the convention B05 reads (`AJE <type>: <reason> | source: <pointer>[; <pointer>]`); the trial balances at year end (adjusted) and at the day before year start (opening). Journeys and tests fill stand-in folders with it; the sample files are read in place and never changed.
- `db/schema/56_qbo.sql`: snapshots, the normalised rows each snapshot holds (accounts, trial balance lines, transactions, journal entries and lines, attachments), all append-only with row-level security on and no policies, `is_test` on every table.
- `src/modules/qbo/index.ts`: the public exports.

## Acceptance checks
1. TB-1: `readBooks` for C01 through `samples` stores a year-end accrual trial balance whose rows equal the golden file and whose debits equal its credits in cents; asking for a cash basis is refused with the reason.
2. TB-10: every read made by `readBooks` (company, two trial balances, transactions per account, journal entries, attachments) has one snapshot row with read-at, sha256, engine and file key; the stored bytes hash to the sha256; reading again writes new dated rows that share the stored files.
3. EV-5, TB-10: every pointer built from a snapshot names the snapshot and the account, and for a transaction its id; a pointer with no snapshot or no account is refused by the schema.
4. TB-10, TB-13: a fake GeneralLedger response with no id column gets each line's Transaction ID from the fake TransactionList by type and number; a line with no match there gets a composite-key pointer marked `idKind: "composite"`; a response with an unknown column, or a TransactionList without its Transaction ID or Memo column, is refused naming the column.
5. OUT-3: the adapter interface and every engine export no write, update or delete method (a type test and a call of every exported function on a spy transport shows only GET requests).
6. ARC-6, ARC-20: `QBO_ENGINE` defaults to `samples`; `sandbox` without its settings and `live` always refuse with their reasons and make no request; `sandbox` switched on in the test with fake setting names runs against the local fake API and returns the same normalised shapes as `samples` for the same fixture company; switching back works (both directions tested).
7. ARC-20: against the fake API, a 429 makes the client wait 60 seconds on the pinned clock and retry; three 429s in a row end in a refusal with the reason; no more than 10 requests go out in any one second.
8. SEC-11: the company named without "(Test)" is refused before any read, by every engine.
9. SEC-10: the settings are logged by name only (a planted setting value never appears in the captured log), and no file under `src/modules/qbo/` matches the gitleaks rules.
10. TB-1: `testworld/qbo/export.ts` for C01 writes a folder whose year-end trial balance equals the answer key's adjusted trial balance in cents, whose transactions count equals the rows in `qbo/*.csv`, and whose journal entries carry every adjusting entry's type, reason and sources in the memo convention.
